# PRD

## 1. 项目背景

本项目是一个基于 Next.js + Supabase 的 AI 项目桌面，面向独立创作者，帮助用户以“项目”为中心收集资料、组织信息、调用 AI、沉淀上下文，并在无限画布中推进创作、研究和产出。

当前阶段开始建设无限画布基础能力。画布能力优先基于开源项目 React Flow / xyflow 进行开发，当前采用官方包 `@xyflow/react`，后续实现应遵循当前项目已有的技术栈、目录结构和代码风格。

## 3. 已确认产品方向

- 产品核心形态是面向项目的 AI 工作空间，而不是单纯的聊天工具、文件夹或白板。
- Zenme 品牌核心含义是将 “zen / 禅” 作为动词，表达通过安静、专注、连接来激发 “me / 我” 自身能力。
- Zenme 品牌视觉优先采用极简黑白体系，以线条、点、节点和连接关系表达“从静到动、由内而外激活”的感觉。
- Zenme 图形标识应避免过度复杂，优先保留少量关键节点和一条激活路径，保证小尺寸下仍然清晰。
- Zenme 图形标识不应简化到失去美感；推荐在主激活路径之外保留 1-2 条辅助连接线和疏密有致的节点层次，让标识兼具克制和生命力。
- Zenme 当前推荐继续基于用户提供的“左侧禅意中心圆环 + 中部点状连接 + 右侧激活节点 + 下方 zenme 字标”方向微调，而不是另起一套视觉语言。
- Zenme 可探索“点线元素直接构成 zenme 字标”的方向，让品牌名本身呈现节点连接与能力激活的视觉语言。
- Zenme 也可探索纯字母标识：以 `me` 为主体，将 `zen` 作为贴近 `me` 的右上角标/指数呈现，表达“我被 zen 激发、放大，如同 me 的 zen 次方”；该方向不需要额外弧线装饰。
- 纯字母标识方向应优先通过字重、字距、比例和角标姿态制造设计感，而不是添加额外装饰；`me` 应稳定有力量，`zen` 应精致贴合并保持指数隐喻。
- 当前品牌 Logo 采用 `docs/images/zenme-exponent-generated-v5-zen-right.png`，前端公共资源路径为 `/brand/zenme-logo-cropped.png`；该公共图应裁掉原图大白边但保留完整 `me` 与右上角 `zen` 字标。首页左侧栏顶部和画布左上角项目状态入口应使用同一品牌图，保持品牌识别一致。
- 用户登录后进入 dashboard 首页，可以创建项目、查看最近项目，并进入项目列表或具体项目画布。
- 项目内部使用无限画布承载资料、图片、文件、节点连接和后续 AI agent 工作流。
- 画布基础能力优先基于 React Flow / xyflow 实现，当前采用 `@xyflow/react`。
- Supabase 相关操作尽可能优先通过 Supabase MCP 完成。
- 涉及用户数据访问时，优先考虑 RLS 策略和最小权限原则。
- 可以先建立轻量设计系统或组件规范，再实现页面。
- 当前首要任务是先把无限画布的基础框架搭建出来。
- 现有中文产品文档暂不优先继续拆分，等无限画布基础框架成型后再按需要整理。
- 项目创建后立即进入画布页。
- Dashboard 最近项目缩略图使用画布快照。
- 项目列表页首期暂不需要搜索、排序、筛选、删除、归档等操作。
- Agent 对话窗口首期需要真正调用模型 API。
- 当前画布统一采用白色点阵画布风格，控制条、节点、菜单和 Agent 面板均优先保持白色轻量视觉体系。
- 文本节点同时承担可编辑内容承载和文本生成入口：保留正文编辑、格式化、复制和作为上下文来源的能力；选中时在下方展开文本生成对话控件。
- 需要对文本内容发起 AI 生成时，应通过节点加号拉线创建“文本生成节点”。文本生成节点是独立画布节点，保存 prompt 和模型，可编辑、可重新提交；提交后生成一个只读 AI 回复子节点。
- AI 回复节点与普通文本节点区分，只保存和展示回答内容，不直接编辑；如果对结果不满意，应回到其父级文本生成节点修改 prompt 后重新生成新的 AI 回复节点。
- 需要对图片发起 AI 编辑时，应通过图片节点加号菜单创建“图片编辑节点”。图片编辑节点使用设置页中配置的图片模型；模型调用使用真实模型 ID，界面展示使用用户配置的显示别名，例如可将 `google/gemini-3.1-flash-image-preview` 显示为 `Nano Banana 2`。用户只填写编辑指令并运行。编辑结果保存为本地项目文件，并生成新的图片节点连接到图片编辑节点。
- OpenRouter API Key 只允许通过本地环境变量 `OPENROUTER_API_KEY` 配置，不写入前端代码、源码文档或提交内容。
- 节点父子级关系首先是 UI 层面的组织关系；只有文本生成等 AI 处理类节点执行任务时，才沿其上下文入边追溯上游节点内容。
- 文本生成节点允许多个父级上下文节点，本质上是上下文有向图而不是单父级树结构；允许文本、Markdown、代码、AI 回复、阅读笔记等多个内容型节点同时作为上下文来源。AI 生成时默认沿入边向父节点和祖先节点追溯 5 层，但不引入兄弟节点。
- 书籍、阅读器、视频、图片、普通文件等资源型节点默认不直接进入 AI prompt；需要先转化为阅读笔记、OCR 文本、转写、摘要或其他内容型节点后再作为上下文。
- 画布应支持多选节点后打组：选中 2 个及以上未分组节点时展示浮动“打组”操作；打组后创建组框节点，将子节点放入组框内并自动排列，移动组框时子节点应跟随移动。
- 当前 UI 中已经沉淀出一组轻量视觉组件，后续页面和画布控件应优先复用，避免继续复制大段 Tailwind class。
- 阅读体系将参考 Inkcode 的阅读能力，在 Zenme 项目画布中重新实现：图书作为画布节点进入项目，阅读器在画布内打开，阅读笔记可生成画布节点并参与 AI 对话。
- 阅读体系的视觉设计必须采用 Zenme 当前风格；Inkcode 只作为能力和布局结构参考，不作为视觉参考。
- 阅读器应在画布内作为 `reader` 节点打开，跟随画布平移、缩放和保存位置，支持移动与调整窗口大小，不应作为模态窗或全屏覆盖层；图书到阅读器的连线应连接节点边缘锚点，而不是外置加号按钮；Inkcode 已有 PDF、EPUB、TXT 阅读能力可作为第一版阅读内核参考；当前阅读资料、笔记和进度运行态已切换到 Supabase 表与 Supabase Storage。
- 图书节点视觉文案应显示为“书籍”，默认图标使用合上的书；阅读器节点视觉文案应显示为“阅读器”，图标使用打开的书。
- 阅读器节点应支持收起和展开：收起时节点尺寸与图书节点保持一致，卡片中标明对应书籍名称和“阅读器”节点身份；收起阅读器时，从该阅读器连接出去的子节点和子连线应同步隐藏，展开时恢复显示。
- 画布缩放统一使用 Ctrl + 鼠标滚轮；阅读器节点内的普通滚轮只滚动阅读内容，不触发画布缩放或平移。
- 按住鼠标中键拖动始终移动画布，即使鼠标位于阅读器节点内部；阅读器内部不使用中键触发自身滚动或拖动。
- 书籍节点应优先使用识别到的书籍封面作为节点图标；PDF 可使用首页渲染图作为封面，EPUB 优先读取包内声明的封面图，TXT 无封面时保留默认书本图标。
- EPUB 性能优先级高于封面完整性：开发阶段拖入 EPUB 时先做轻量登记，不在拖入主链路同步提取 EPUB 内封面；阅读器应参考 Inkcode 滚动模式，将 EPUB 预处理为固定页面对象并在滚动模式中按页堆叠，前端只渲染视口附近页面，避免大 EPUB 导入或打开时造成画布严重卡顿。
- EPUB 页面内容区应采用固定版心宽度，参考 Inkcode 的 600px 页面宽；调整阅读器节点外框大小时，不应改变 EPUB 正文排版宽度，只改变阅读器可视区域、滚动范围和两侧留白。
- EPUB 正文如果识别为中文内容，应对正文段落应用首行缩进两个字；非中文 EPUB 不应用中文段落缩进。
- EPUB 正文默认段落间距应设为 1.5em；以 100% 内容缩放为例，正文 16px 字号对应 24px 段后距。正文行高保持 32px。
- EPUB 和 PDF 阅读器需要提供内容缩放控件，支持缩小、放大和恢复 100%；该控件只改变阅读内容自身大小，不改变画布缩放，也不改变阅读器节点外框大小。
- EPUB 和 PDF 在内容缩放为 100% 时，应使用一致的默认内容宽度基准；当前基准宽度为 600px，避免同为 100% 时两种格式视觉尺寸明显不一致。
- 阅读器正文/PDF 选区浮动控件中，点击颜色即创建对应颜色的标注，不再额外展示“标注”按钮；需要补充备注时仍可使用右侧笔记栏保存。
- 阅读器右侧标注栏按创建时间从旧到新展示；新标注创建后追加到列表底部，并立即滚动到底部；每条标注需要显示完整创建时间，包含年月日时分秒。
- 阅读器右侧笔记卡片中的六点拖拽手柄只用于调整笔记列表顺序，不用于创建画布节点；调整后的笔记顺序需要持久化保存，刷新后保持一致。创建笔记画布节点继续通过卡片内“创建画布节点”按钮触发。
- 笔记拖拽排序时，应在即将插入的两个卡片之间显示明显的占位间距或插入提示，并带有轻量动画，避免只靠边框变化提示位置。
- 阅读体系一期已确认：只通过图书节点加号菜单打开阅读器并创建连线；阅读器首期只支持滚动模式；同一笔记可创建多个画布节点；笔记节点默认连接原图书节点；Agent 首期只引用单个笔记节点；AI 拆书不进入首期。
- 阅读器笔记应逐步升级为 Inkcode 类似的 `Annotation` 标注模型：EPUB/TXT 保存 `offset`、`length`、`color`、`type` 并在正文中重绘高亮；PDF 阅读窗口应以 PDF.js canvas 渲染，并区分可选中文字 PDF 与纯图片 PDF：文本型 PDF 渲染 text layer，优先支持文字选择标注；图片型 PDF 退回 overlay 区域拖拽标注，保存页内百分比 `rect`；右侧笔记栏与正文/页面高亮消费同一份标注数据。

### 3.1 2026-06-26 当前版本实现记录

本节记录截至 2026-06-26 已经确认并落地的产品和技术决策，后续开发应在此基础上继续迭代。

#### 3.1.1 画布节点与连线

- 画布节点的左右白色连线端点不再无条件显示，而是根据真实入边和出边计算显示状态：
  - 有入边：显示左侧白点。
  - 有出边：显示右侧白点。
  - 没有任何连线：左右白点都不显示。
- 为保证自动创建节点后连线立即可见，React Flow handle 需要保持渲染，只在视觉上隐藏无连接端点；不要通过卸载 handle 的方式隐藏端点。
- `hasIncomingEdge`、`hasOutgoingEdge` 属于运行时渲染状态，只由当前 `edges` 计算，不应写入持久化快照或历史快照。
- 自动创建的节点，例如文本生成提交后产生的 AI 回复节点、阅读器笔记卡片创建的笔记节点，创建后应立即显示连线，不需要刷新页面。
- 手动从节点加号拖线创建的节点，应优先落在用户拖线终点，不应被自动子节点排列逻辑覆盖。
- 自动生成的子节点可以使用“追加到最新子节点下方”的规则，避免覆盖已有子节点；该规则用于 AI 回复节点和阅读笔记卡片创建节点等自动生成场景。
- 空白画布中需要显示一个类似节点但视觉更轻的提示容器，仅保留边框，不使用阴影；文案居中分两行展示：“双击画布创建一个节点”“或上传一本书、一张图片、一段文字...”。该提示不是节点，不参与保存、连线、拖动、历史记录或缩略图生成，拥有任意真实节点后自动隐藏。
- 双击画布打开的添加面板应支持直接创建“文本生成”节点；面板中不再展示图片、视频、音频、3D 世界等不可用占位选项；“上传”入口应打开系统文件选择窗口，并复用拖拽文件进入画布的同一套节点创建、预览、登记和上传逻辑。
- 节点重叠时，点击某个节点应提升该节点的 `zIndex`，让用户点击的节点显示到上层。
- 连线表达节点之间的上下文或引用关系；用户应可以选中连线后按 Delete/Backspace 删除连线，从而断开上下文关系，且该操作应进入撤销历史。
- 文本类生成入口可以反向拖线连接到文本、Markdown、代码、AI 回复、阅读笔记等内容型节点，以绑定该节点作为生成上下文；系统保存时应归一为“上下文节点 -> 当前文本类节点”的关系，保证生成请求能追溯到上游上下文。
- 文本生成节点的上下文入边允许多条；多个上游节点共同构成一次生成请求的上下文集合。实现中不得用单个 `parentId` 覆盖或替代多入边关系，也不应因为新增一个上游上下文而移除已有上下文。
- 节点作为连线目标时，连接入口应具备较大的命中区域；无连线时不常驻显示白点，但在节点 hover、已有入边或拖线靠近/可连接时应显示吸附反馈，降低连接大节点时的命中难度。

#### 3.1.2 节点类型分层

- 资源型节点：承载原始外部资料，默认不直接进入 AI prompt，包括书籍、阅读器、图片、视频、音频、普通文件等。
- 内容型节点：承载可直接阅读、复制、编辑或引用的文本化内容，可作为 AI 上下文来源，包括文本、Markdown、代码、阅读笔记、OCR 文本、音视频转写、人工整理摘要等。
- 处理型节点：承载一次 AI 或工具处理任务，保存输入、模型、参数和执行状态；当前已确认文本生成节点属于处理型节点，后续图像生成、总结、拆解、转写等可以按需要独立成处理型节点，也可以在同一处理框架下通过定向 prompt 区分。
- 结果型节点：承载处理型节点生成的结果，默认只读或弱编辑，包括 AI 回复节点、图像生成结果、视频处理结果、结构化提取结果等。
- UI 父子级关系不等于 AI 上下文关系。普通父子线主要服务生成来源、布局、收起、排列和视觉组织；只有处理型节点执行任务时，才解释其入边为上下文来源。处理型节点应支持多条上下文入边，形成多父级上下文图。

#### 3.1.3 文本节点

- 文本节点是可编辑富文本节点，并在选中时承担底部 AI 提问/续写入口职责。
- 文本节点支持调整大小，四边和四角都应可调整，调整后的尺寸需要进入画布状态和持久化快照。
- 文本节点标题默认为“文本”，不会随正文内容自动变化。
- 文本节点标题区域支持双击编辑标题；标题左侧图标区域作为拖动手柄，hover 时显示手型。
- 文本节点内容编辑区应显示正常输入光标，支持从其他文件或网页粘贴纯文本；失焦后应清除选区高亮。
- 文本节点富文本能力首期支持：
  - Bold
  - Italic
  - Underline
  - inline code
- 文本节点工具栏中的“创建画布节点”按钮可将当前选中文本创建为该文本节点的子节点。
- 文本节点内部滚动条不得超出节点圆角；不应显示浏览器默认上下三角按钮。

#### 3.1.4 Markdown 节点

- Markdown 节点可通过画布双击添加菜单创建，节点名称和类型为“Markdown”。
- Markdown 节点用于承载 Markdown 源文本，并在编辑时实时渲染预览。
- Markdown 节点编辑态应显示 Markdown 源文本，保证输入光标与源文位置一致；失焦后显示渲染结果，且不得清空内容。
- Markdown 节点支持调整大小，四边和四角都应可调整，调整后的尺寸需要进入画布状态和持久化快照。
- Markdown 节点内容以 Markdown 源文本保存到 `plainText`；`richTextHtml` 后续写回为空。
- Markdown 节点能力首期支持：
  - 标题：`#`、`##`、`###`
  - 粗体：`**text**`
  - 斜体：`*text*`
  - 下划线：`<u>text</u>`
  - 行内代码：`` `code` ``
  - 代码块：三个反引号围栏代码块
  - 引用：`> quote`
  - 无序列表：`- item`
  - 链接：`[text](url)`
- Markdown 节点工具栏按钮向当前选区插入对应 Markdown 标记，并即时保存和渲染。
- Markdown 节点工具栏中的“创建画布节点”按钮可将当前选中文本创建为该 Markdown 节点的子节点。

#### 3.1.5 代码节点

- 代码节点可通过画布双击添加菜单创建，节点名称和类型为“代码”。
- 代码节点用于承载代码片段，支持调整大小，尺寸需要进入画布状态和持久化快照。
- 代码节点标题默认显示“代码”，支持双击标题文字修改名称；标题左侧图标区域作为拖动手柄，hover 时显示手型；代码编辑区域不作为拖动区域。
- 代码节点顶部提供编程语言选择，首期支持 Python、JavaScript、TypeScript、TSX、HTML、CSS、JSON、SQL、Shell、Go、Rust、Java、C++、C# 和 Plain Text。
- 代码节点正文区域支持代码输入、复制和滚动；输入内容需要保存到画布快照。
- 代码节点内容编辑后需要自动写回画布状态，不能只依赖失焦保存；当代码节点作为文本生成节点的上游上下文时，文本生成请求必须带入最新代码内容和语言。
- 代码节点正文应根据所选语言进行基础语法高亮，首期至少区分关键字、字符串、数字和注释。
- 代码节点视觉应保持 Zenme 白色风格，内部效果参考轻量代码编辑器。

#### 3.1.6 文本生成节点

- 文本生成节点通过节点加号拖线菜单创建，节点名称和类型为“文本生成”。
- 文本生成节点是独立画布节点，用于保存用户的生成 prompt 和模型选择。
- 文本生成节点 UI 参考原底部提问组件，但作为节点存在于画布中。
- 文本生成节点可编辑 prompt，可重新提交；重新提交会生成新的 AI 回复子节点，不直接覆盖旧回复。
- 文本生成节点支持调整大小，尺寸需要进入画布状态和持久化快照。
- 文本生成节点可作为上下文聚合节点：生成时沿所有入边追溯父节点和祖先节点上下文，默认追溯 5 层，不引入兄弟节点；多个父级上下文需要按稳定顺序共同组织进 prompt。
- 文本生成节点左侧提供“绑定上游上下文”的连接入口，用户可从该入口拖线到文本、Markdown、代码、AI 回复、阅读笔记等内容型节点；右侧加号保留为向下创建/生成节点入口。
- 上下文绑定应从文本生成节点左侧加号发起；拖线靠近上级节点时，上级节点靠近拖线的一侧应显示白色着陆点并提供吸附反馈，不作为用户主动发起向上连线的入口。
- 正在进行上下文绑定连线时，目标节点的普通右侧“创建子节点”加号应隐藏，避免与上下文着陆点混淆。
- 当前上下文组织规则：
  - 文本节点提供标题和纯文本内容。
  - Markdown 节点提供标题和 Markdown 源文本内容。
  - 代码节点提供语言和代码内容。
  - AI 回复节点提供标题和回复内容。
  - 阅读笔记节点提供来源书籍、原文和备注。
  - 资源型节点默认不提供正文上下文；如链路中出现书籍、阅读器、图片、视频或文件节点，仅可提供轻量元信息，或直接跳过，不得将大型 PDF、EPUB、视频、图片二进制或全文内容塞入 prompt。
  - 文本生成节点提供自身 prompt。
- 当前文本生成节点使用 `/api/ai/chat` 的统一系统提示词；文本生成节点自身尚未单独维护 system prompt 模板。
- 模型配置不再沿用 Claude Code 的 Haiku/Sonnet/Opus 语义作为用户侧主模型体系；Zenme 以“服务商 + 明确模型 ID 列表”为准。服务商配置中维护已添加模型，模型可启用/屏蔽，并声明文本、视觉、图片、向量、音频、排序、工具等模态。文本节点、文本生成节点和 Agent 只展示已启用且具备“文本”模态的模型；图片编辑节点只使用具备“图片”模态的图片模型。智谱等支持模型列表接口的服务商允许用户手动触发拉取，拉取结果只作为候选池，需用户选择后才加入已添加模型；OpenRouter 模型池过大，当前不自动拉取，由用户手动维护需要的模型。

#### 3.1.7 AI 回复节点

- AI 回复节点与文本节点区分，定位为只读结果节点。
- AI 回复节点不再显示“提问”和“回答”两个内部标题；提问内容由父级文本生成节点保存。
- AI 回复节点正文直接展示回复内容，正文区域使用浅灰只读面板，以明显区别于可编辑文本节点。
- AI 回复节点支持复制回复内容。
- AI 回复节点正文区域支持内部滚动；鼠标悬停在正文区域滚动时，应滚动回复内容，而不是被画布滚轮逻辑截获。
- AI 回复节点支持调整大小，尺寸需要进入画布状态和持久化快照。
- 如果用户对 AI 回复不满意，应回到其父级文本生成节点修改 prompt 并重新提交，生成新的 AI 回复节点。

#### 3.1.8 阅读器与阅读笔记

- 阅读器节点位于画布内，不是模态窗；应跟随画布缩放和平移。
- 阅读器节点支持移动、调整大小、收起和展开。
- 阅读器收起时使用与书籍节点接近的卡片大小，并标注对应书籍和“阅读器”身份；收起阅读器时隐藏其子节点和相关子连线。
- 阅读器 header 高度应尽量紧凑，不应在上边界留下大块空白区域。
- 阅读器中目录字体较小，目录栏支持调整宽度和收起；调整目录宽度不应改变 EPUB/PDF 内容版心宽度。
- 阅读器右侧笔记栏支持拖动左侧边界调整宽度，宽度范围为 220px 到 700px；调整笔记宽度只改变笔记栏可视空间，不应改变 EPUB/PDF 内容版心宽度。
- EPUB 与 PDF 都需要内容缩放控件，内容 100% 时使用一致的默认宽度基准。
- EPUB 使用固定版心和分页滚动模式，阅读器外框变宽不改变正文版心宽度。
- EPUB 中文内容正文段落首行缩进两个字，段落间距为 1.5em。
- PDF 文本型页面使用 I 形文本选择光标；EPUB 正文也应使用文本选择光标，不应显示为手型。
- 阅读器标注浮动控件应出现在选区上方，避免遮挡所选内容；EPUB 和 PDF 需要统一标注浮动体验。
- 阅读器右侧笔记栏按创建时间从旧到新展示，新标注追加到底部并立即滚动到底部。
- 阅读笔记卡片创建画布节点时，应创建为阅读器节点的子节点，并按已有子节点向下排列。
- 从阅读笔记卡片拖拽到画布创建节点时，应按拖拽终点创建，不走自动排列规则。

#### 3.1.9 分组与画布辅助控件

- 多选节点后可通过浮动工具栏打组。
- 分组框视觉为透明框，标题位于框外；选中状态边框与普通节点选中边框保持一致。
- 组内节点可以拖出组框解除分组。
- 拖动分组框时，组内节点应跟随移动。
- 点击分组后，仍应可以继续点击组内节点。
- 小地图尺寸为 `200px × 150px`，底部控制条宽度与小地图对齐，保持白色轻量风格。
- 小地图控制条移除不需要的减号和问号按钮，保留小地图开关、网格、重置视图和缩放滑杆。

#### 3.1.10 首页与项目缩略图

- Dashboard 首页左侧新建项目入口和最近项目中的新建项目卡片都应可创建项目。
- 首页最近项目卡片中的新建项目卡片和项目缩略图卡片需要对齐。
- 项目缩略图使用 16:10 比例展示。
- 画布中点击项目名称位置可以编辑项目名称。

#### 3.1.11 性能观测与优化

- 已建立画布性能观测能力，开启 `NEXT_PUBLIC_ZENME_PERF_DEBUG=1` 后可采集性能指标。
- 最近性能指标保存在 `window.__ZENME_CANVAS_PERF__`，可通过 `window.__ZENME_CANVAS_PERF_SUMMARY__()` 查看汇总。
- 支持 `?zenmePerfSeed=200&zenmePerfSeedReplace=1` 生成大画布测试数据。
- 支持 `zenmePerfEdgesPerRow` 增加连线密度，支持 `zenmePerfSample` 和 `zenmePerfSampleThumbnail` 触发采样。
- 当前已做的性能止血包括：
  - 拖动和 resize 过程中跳过中间帧历史记录，只记录操作结束状态。
  - 文本节点正文输入改为局部编辑和防抖写回。
  - 本地快照保存优先 IndexedDB，localStorage 只作为兼容和兜底。
  - 保存请求和本地快照写入支持并发合并。
  - 拖动和 resize 过程中暂停 MiniMap 重渲染，交互结束后恢复。
  - 缩略图刷新周期降低，避免频繁 DOM 截图。
  - 持久化前剥离运行时字段、函数和测量字段。
- 性能调研详情记录在 `/docs/无限画布性能优化调研报告.md`。

## 6. 技术决策

- 前端框架：Next.js。
- 后端与数据服务：Supabase。
- 无限画布基础库：React Flow / xyflow，当前采用 `@xyflow/react`。
- 模型/API 接入参考 `/docs/api/` 下的文档。
- 前端只能使用 `NEXT_PUBLIC_` 开头的公开环境变量。
- 不得将 Supabase service role key、数据库密码、访问令牌、第三方 API Key 等敏感信息写入前端代码或提交到仓库。
- 第三方模型 API Key 只能存放在 `.env.local` 或部署平台环境变量中，文档中只记录环境变量名和接入说明。
- 智谱 API 已完成本地最小调用测试，模型列表和对话补全接口可用，精简接入文档见 `/docs/api/api.md`。
- 模型选择列表首期可以使用固定列表，优先使用已验证可用模型；后续可增加服务端模型探测接口。

### 6.1 xyflow 可直接提供的能力

`@xyflow/react` 可以作为画布核心底座，直接提供或较低成本支持以下能力：

- 节点与连线的数据模型：使用 `nodes` 和 `edges` 表达画布中的对象与关系。
- 画布交互：节点拖动、画布缩放、画布平移、选择、多选等基础交互。
- 自定义节点：文件节点、图片节点、文本节点、AI 输出节点、任务节点等都可以作为 React 组件实现。
- 自定义连线：支持默认连线、自定义边、边标签和后续边操作。
- 连接点：通过 `Handle` 实现节点连接点，可支持多个 source/target handle。
- 小地图：通过 `MiniMap` 实现画布缩略图。
- 画布控件：通过 `Controls` 或自定义控件实现放大、缩小、重置位置等能力。
- 背景网格：通过 `Background` 实现画布背景网格。
- 网格吸附：通过 `snapToGrid`、`snapGrid` 等配置实现节点移动时的网格对齐。
- 节点工具栏：通过 `NodeToolbar` 或自定义节点 UI 实现节点选中/hover 后的操作入口。
- 节点尺寸调整：后续可通过 `NodeResizer` 支持图片、文件卡片等节点调整尺寸。
- 保存与恢复：可通过保存 `nodes`、`edges` 或 React Flow instance 的序列化结果实现画布持久化。

### 6.2 xyflow 不能直接解决、需要项目自研的部分

以下能力不属于 `@xyflow/react` 的完整业务职责，需要在项目层自行实现：

- Dashboard 首页、项目列表页、项目权限、用户头像等业务页面与数据。
- 从操作系统拖入文件/图片后的文件读取、类型判断、缩略图生成、上传与错误处理。
- Supabase Storage 上传、文件元数据保存、RLS 策略与最小权限控制。
- 项目、画布、节点、边的数据表设计和持久化策略。
- 自动保存、保存状态、冲突处理、离线状态等业务逻辑。
- Agent 对话窗口、模型选择、消息流、API 调用和上下文注入。
- 项目缩略图生成、画布快照和最近项目展示逻辑。
- 节点操作菜单中的具体业务动作。

### 6.3 画布一期建议组件拆分

第一阶段实现画布时，建议按以下模块拆分：

- `CanvasPage`：画布页整体布局，包含 header、sidebar、agent 入口和画布容器。
- `ProjectCanvas`：封装 `@xyflow/react` 的 `ReactFlow`、nodes、edges、事件处理和画布状态。
- `ImageNode`：图片节点，展示图片内容或缩略图。
- `FileNode`：文件节点，展示文件基础信息。
- `NodeActionMenu`：点击节点加号后的操作菜单。
- `CanvasControls`：小地图开关、网格吸附、重置位置、放大、缩小等画布控件。
- `AgentPanel`：画布内 agent 对话窗口。

### 6.4 画布数据持久化方向

初期可以先使用前端 state 完成交互闭环，随后再落到 Supabase：

- `projects`：项目基础信息，如名称、创建时间、更新时间、封面或缩略图。
- `canvas_nodes`：画布节点数据，如节点类型、位置、尺寸、业务数据、所属项目。
- `canvas_edges`：画布连线数据，如 source、target、handle、边类型、所属项目。
- `project_files` 或 Storage 关联表：记录拖入文件/图片的存储路径、类型、大小、缩略图等元数据。
- 或在早期使用 `canvas_snapshots` 存储整个画布 JSON，降低第一版数据结构复杂度。

### 6.5 当前视觉组件约定

当前已经根据现有 UI 提炼出 `components/zenme/visual-components.tsx`，用于承载项目内重复出现的视觉原语。后续新增页面和画布控件时，应优先复用这些组件，再按需要扩展。

现有视觉组件：

- `ZenmeIconButton`：圆形图标按钮，用于画布左侧浮动工具栏、右下角 Agent 入口等轻量操作入口。
- `ZenmeControlButton`：底部画布控制按钮，用于小地图开关、网格吸附、重置、缩放、帮助等工具按钮。
- `ZenmeModelPicker`：模型选择 dropdown，采用紧凑圆角按钮和自定义弹出菜单，避免原生 `select` 弹层贴边且难以统一样式。
- `ZenmeCopyButton`：对话消息下方的复制按钮，默认 hover 时显示，保持对话区视觉干净。

视觉原则：

- 默认采用白色、浅灰边框、细阴影和 `8px` 左右圆角，画布浮动入口可使用圆形按钮。
- 控件应尽量使用图标按钮并通过 `title` 提供含义。
- 不要在页面中重复散落大段 Tailwind class；如果某类控件重复出现，应沉淀到视觉组件。
- 视觉组件只负责外观和基础交互包装，不承载项目业务数据、Supabase 操作或画布状态管理。

## 10. 待确认问题推荐方案

### 10.1 画布节点与边的数据结构

采用方案：首期使用 `@xyflow/react` 原生 nodes/edges 结构作为前端状态和快照主体，在 `data` 字段中承载业务信息。

节点建议结构：

```ts
type CanvasNodeData = {
  kind: "image" | "file" | "text" | "agent";
  title: string;
  fileId?: string;
  previewUrl?: string;
  originalUrl?: string;
  mimeType?: string;
};
```

边建议结构：

```ts
type CanvasEdgeData = {
  kind?: "default" | "reference" | "generated";
  label?: string;
};
```

首期原则：

- 不急着为每一种节点建复杂表结构。
- 先让画布能稳定创建、移动、连接、保存和恢复。
- 文件、图片等资源元数据可以单独存表，节点只引用 `fileId`。
- 后续如果需要协作、版本历史、节点级查询，再拆分 `canvas_nodes` 和 `canvas_edges`。

### 10.2 保存状态

采用保存状态：

- `未保存`：本地有改动，但还未触发保存。
- `保存中`：正在写入 Supabase。
- `已保存`：最近一次保存成功。
- `保存失败`：最近一次保存失败，需要允许用户重试。
- `离线`：浏览器离线或无法连接服务端，暂时只保留本地状态。

交互建议：

- header 中展示项目名称旁边的保存状态。
- 用户编辑画布后立即进入 `未保存`。
- 2 分钟自动保存或点击手动保存时进入 `保存中`。
- 保存成功后进入 `已保存`，并记录 `last_saved_at`。
- 保存失败时展示 `保存失败`，不丢弃本地画布状态。

### 10.3 Supabase 数据表、RLS 策略和 Storage Bucket

采用首期数据表：

```sql
projects
- id uuid primary key
- owner_id uuid
- name text
- prompt text
- model text
- thumbnail_path text
- created_at timestamptz
- updated_at timestamptz
- last_saved_at timestamptz

canvas_snapshots
- id uuid primary key
- project_id uuid
- owner_id uuid
- snapshot jsonb
- created_at timestamptz
- updated_at timestamptz

project_files
- id uuid primary key
- project_id uuid
- owner_id uuid
- original_path text
- preview_path text
- file_name text
- mime_type text
- size_bytes bigint
- created_at timestamptz
```

采用 Storage Bucket：

- `project-assets`：存储用户拖入画布的文件、图片原图、图片压缩图、画布快照缩略图。

采用 Storage 路径：

```text
{user_id}/{project_id}/original/{file_id}.{ext}
{user_id}/{project_id}/preview/{file_id}.webp
{user_id}/{project_id}/thumbnail/latest.webp
{user_id}/{project_id}/reading/original/{asset_id}.{ext}
{user_id}/{project_id}/reading/covers/{asset_id}.{ext}
```

Storage object key 不拼接用户上传的原始文件名，原始文件名仅保存在业务表字段中，用于界面展示和下载响应头。

RLS 原则：

- 所有业务表开启 RLS。
- 用户只能读取、创建、更新、删除自己的项目数据。
- `projects.owner_id = auth.uid()` 是项目权限的核心判断。
- `canvas_snapshots.owner_id = auth.uid()`，并且 `project_id` 归属当前用户。
- `project_files.owner_id = auth.uid()`，并且 `project_id` 归属当前用户。
- Storage 只允许 authenticated 用户访问自己路径下的对象。
- Storage 上传策略需要同时考虑 `INSERT` 和 `SELECT`，因为 Supabase Storage 上传后会返回对象元数据；缺少匹配的 `SELECT` policy 可能导致上传失败。

### 10.4 画布持久化方案

采用方案：首期采用整体 `canvas_snapshots` JSON，不先拆 `canvas_nodes` / `canvas_edges`。

原因：

- 当前首要任务是搭出无限画布框架。
- React Flow 的 nodes/edges 天然适合序列化为 JSON。
- 首期需求更关注画布整体恢复，而不是节点级搜索、协作或审计。
- JSON 快照实现成本低，适合快速验证交互和产品感觉。

建议落地方式：

- 前端维护 `nodes`、`edges`、`viewport`。
- 保存时写入：

```ts
type CanvasSnapshot = {
  version: 1;
  nodes: Node[];
  edges: Edge[];
  viewport: {
    x: number;
    y: number;
    zoom: number;
  };
  updatedAt: string;
};
```

- `projects` 表保存项目列表需要的轻量信息。
- `canvas_snapshots` 表保存当前最新画布状态。
- 后续如需要版本历史，可以从“单条最新快照”升级为“多条历史快照”。
- 后续如需要节点级查询、协作、局部更新，再引入 `canvas_nodes` 和 `canvas_edges` 拆表。

## 12. OCR 能力接入

### 12.1 已确认需求

- 图片型/扫描型 PDF 不做整本 OCR。
- 用户在 PDF 阅读器中框选页面区域后，对该框选区域截图并执行 OCR。
- OCR 结果应作为区域标注的 `selectedText`，进入右侧笔记栏，并可继续创建画布笔记节点。
- 文本型 PDF 仍优先使用 PDF text layer 选择文字，不强制走 OCR。

### 12.2 技术方案

- 阅读器端沿用 Inkcode 的思路：高分辨率渲染当前 PDF 页，按页内百分比 `rect` 裁剪框选区域，再把裁剪图片交给 OCR。
- Zenme 通过服务端 `/api/reading/ocr` 调用 OCR，不在前端暴露密钥。
- OCR provider 支持切换：
  - `local-model`：开发测试使用本地模型。当前采用 `tesseract.js`，语言为 `chi_sim + eng`；语言包来自 `@tesseract.js-data/chi_sim` 与 `@tesseract.js-data/eng`，运行时复制到 `data/ocr-models/tessdata`，缓存目录为 `data/ocr-models/tesseract-cache-v2`。
  - `tencent`：腾讯云 OCR 技术验证与云端上线候选。默认使用 `GeneralAccurateOCR`，适合扫描型讲义、题库这类小字和复杂版面场景；可降级到 `GeneralBasicOCR` 做成本/速度对比。
- 腾讯云密钥只允许放在服务端环境变量：
  - `TENCENT_CLOUD_SECRET_ID`
  - `TENCENT_CLOUD_SECRET_KEY`
  - `TENCENT_CLOUD_REGION`

### 12.3 约束与决策

- 腾讯云 OCR 不直接接收整本 PDF，避免 PDF/Base64 大小限制和不必要的成本。
- 首期只识别用户框选区域，不自动批量扫描整页或整本书。
- 本地模型文件和缓存不提交到 Git，统一忽略 `data/ocr-models/`。
- 已在对话中暴露过的腾讯云密钥需要在后续正式使用前轮换。

### 12.4 最新交互变更

- 图片型 PDF 的区域 OCR 标注默认生成灰色临时框，点击颜色后才保存为正式标注和笔记卡片。
- 临时框选区域支持再次调整：按住框选内部可拖动位置，拖动边界或控制点可调整范围。
- 停止拖动或缩放临时框后，应重新裁剪当前区域并重新执行 OCR，右侧草稿内容同步更新。
- 图片型 PDF 的框选只响应鼠标左键；鼠标中键在阅读器内部拖动时仍用于移动画布，不应触发框选。
- 阅读器内容缩放比例应随阅读进度一并保存；刷新页面或重新打开同一本书时，应恢复上次设置的缩放比例。
- 阅读器应保存当前阅读位置，包括当前页/章节与页内滚动比例；刷新页面或重新打开同一本书时，应尽量恢复到刷新前的同一位置，而不是只回到页首。

## 13. 文本节点交互

### 13.1 已确认需求

- 文本节点内容区点击即可进入编辑，不再以“双击”作为用户提示。
- 空文本节点未获得焦点时，内容区 placeholder 显示为“点击此处编辑文本”。
- 空文本节点获得焦点后，不显示 placeholder，避免与输入光标和编辑状态混淆。
- 空文本节点失去焦点后，如果内容仍为空，则恢复显示 placeholder。
- 文本、Markdown、代码片段统一收敛为“文本节点”，不再作为三个独立的新建节点入口。
- 文本节点选中后在节点上部展示显示方式控件，支持在“纯文本”“Markdown”“代码”之间切换。
- 选择“代码”显示方式时，文本节点上部控件应显示语言子选项，首期支持 Python、JavaScript、TypeScript、TSX、HTML、CSS、JSON、SQL、Shell、Go、Rust、Java、C++、C# 和 Plain Text。
- 旧版 Markdown 节点和代码节点需要兼容为统一文本节点渲染，避免历史画布内容失效。
- 文本生成交互合并进文本类节点：文本节点继续保留原有正文编辑、格式化、显示模式切换和代码语言选择能力；同时，选中节点时在节点下方以浮层形式展开文本生成对话控件。AI 回复节点和阅读笔记节点也应支持选中后展开同一套对话控件。
- 文本类节点下方对话控件提交后，应以当前节点自身内容和上游上下文共同作为模型上下文，在右侧/下方生成 AI 回复子节点并自动连线。
- 文本类节点下方对话控件需要按节点保存上一次使用的 prompt 和模型选择；重新选中节点时，应恢复该节点自己的上次输入状态，而不是回到全局默认值。
- 文本生成产生的 AI 回复子节点需要继承本次文本生成所使用的文本模型选择，后续在该回复节点继续提问时默认沿用同一文本模型；该状态只使用文本生成字段，不与图片编辑节点的图片模型、比例和清晰度状态混用。
- 文本节点左侧应提供“绑定上游上下文”的加号连接入口；无上游父节点时，不应常驻或 hover 显示代表已连接端点的白点，只有已有入边时才显示左侧连接端点白点。
- 合并后，文本生成不再要求用户先创建独立“文本生成节点”。历史画布中的独立文本生成节点仍需兼容渲染和提交，避免旧数据失效。

## 14. 首页项目与缩略图

### 14.1 已确认需求

- 首页“最近项目”应按最近打开顺序排列，而不是只按创建时间或保存时间排列。
- 项目缩略图只展示画布内容本身，包含节点和节点连线。
- 项目缩略图不应包含应用固定 UI，包括左侧工具栏、项目状态栏、小地图、底部控制条、Agent 面板、临时菜单、React Flow 水印和画布点阵背景。
- 空画布不应生成空白缩略图；需要等画布中存在节点后再写入缩略图。
- 缩略图规则变更时应通过版本号让旧缩略图失效，避免首页继续展示包含旧 UI 的历史缩略图。

## 15. 图片编辑节点

### 15.1 已确认需求

- 图片编辑节点本体只展示待生成图片框；选中节点时，下方输入区以浮层弹窗形式出现，不参与节点尺寸。
- 图片编辑节点输入浮层应在画布缩放时保持合理的屏幕尺寸，避免随画布缩放过小或过大。
- 图片编辑节点点击图片框区域即可选中，选中后显示输入浮层。
- 图片编辑节点的连线锚点位于图片框中线。
- 图片编辑成功后，结果图应原地替换图片编辑节点，保留原有连线位置，不再在右侧追加新的结果节点。
- 图片编辑结果节点应使用“图片生成”黑色卡片样式，不复用普通上传图片节点的替换按钮和上传状态展示。
- 图片编辑结果节点仍应保留图片编辑能力：用户再次选中结果图后，下方弹出输入浮层，可继续提交新的编辑指令。
- 图片编辑结果节点重新提交时，应以当前结果图作为参考图；等待新结果返回期间保留上一次生成图片，只显示编辑中状态，接口成功后再用新结果原地覆盖旧结果。
- 图片编辑节点和图片编辑结果节点下方输入控件需要按节点保存上一次使用的编辑 prompt、比例和清晰度选择；重新选中节点时恢复该节点自己的上次输入状态。
- 图片编辑结果节点的画布展示尺寸与真实图片像素解耦；即使选择 `4K` 或更高分辨率，也只按固定画布卡片尺寸展示，下载或打开原图时才使用真实像素尺寸。
- 图片节点和图片编辑结果节点选中后，应在图片上方显示图片工具条，首期包含“最大化查看”和“下载原图”两个图标按钮。
- 最大化查看应以深色沉浸浮层展示，居中显示原图，右侧展示提示词、模型、质量、宽高比等信息，并提供下载入口；按 Esc 或点击关闭按钮可退出预览。
- 下载行为应使用节点 `originalUrl` 下载真实原图；画布上的缩略显示不影响下载文件尺寸。
- 图片下载文件名应优先使用节点元数据中的原始文件名，其次使用节点标题，并追加本地时间戳；扩展名优先沿用原始文件名或响应 MIME 类型，避免多次下载互相覆盖。
- 图片编辑节点支持尺寸选择，当前包含清晰度和比例：
  - 清晰度：`512P`、`1K`、`2K`、`4K`。
  - 比例：`自适应`、`1:1`、`9:16`、`16:9`、`3:4`、`4:3`。
- 尺寸选择不作为独立图片 API 参数传递；选项背后应转换为图片编辑 system prompt，和用户输入的编辑指令一起提交给图片模型。
- 图片编辑 system prompt 应明确：模型身份是图片编辑模型，任务是基于参考图执行编辑而不是重新生成无关图片；必须尽可能保持主体完整性、主体身份、数量、姿态、结构、关键细节、构图、透视、光照和背景关系，只修改用户明确要求修改的内容。
- 默认尺寸选择为 `16:9 · 1K`。

## 16. 模型配置

### 16.1 已确认需求

- 设置页需要增加“模型配置”入口，用于管理本地模型服务商。
- 模型服务商管理交互参考 cc-haha：
  - 左侧设置分类中包含“模型配置”。
  - 右侧展示服务商列表，支持添加、编辑、删除、设为默认。
  - 服务商编辑以弹窗呈现，包含名称、备注、接口地址、API 格式、认证方式、开关项、API 密钥、模型映射、上下文窗口和设置 JSON。
- 模型服务商需要支持模型映射，首期字段包括：
  - 主模型：默认文本生成和 Agent 模型。
  - Haiku 模型：轻量/快速模型。
  - Sonnet 模型：常规/均衡模型。
  - Opus 模型：高能力模型。
  - 图片模型：图片生成和图片编辑节点使用的模型。
- 模型需要支持“模态”能力标记，参考 Cherry Studio 的模型模态选择方式；首期模态包括：文本、视觉、图片、向量、音频、排序、工具。
- 每个模型可配置上下文窗口大小；后续文本生成、Agent、图片编辑和多模态节点应基于模型模态与上下文窗口选择可用模型。
- API Key 属于本地敏感配置，只允许保存到本地数据目录的 `settings.json` 或本机环境变量，不写入源码、PRD 示例或提交内容。
