# 无限画布性能优化调研报告

更新时间：2026-06-26

## 1. 调研目标

当前用户反馈无限画布“每次操作都会卡顿”，影响节点拖动、文本输入、阅读器操作和 AI 子节点生成等核心体验。本报告用于确认卡顿原因，制定优化目标，并形成分阶段优化计划。

## 2. 当前架构观察

画布核心实现位于：

- `components/zenme/canvas-client.tsx`
- `components/zenme/canvas/geometry.ts`
- `components/zenme/canvas/persistence.ts`
- `components/zenme/canvas/rendered-nodes.ts`
- `components/zenme/nodes.tsx`
- `components/zenme/reading-workspace.tsx`

当前画布基于 `@xyflow/react` 管理节点与连线，主要状态包括：

- `nodes`
- `edges`
- `canvasViewport`
- `canvasHistory`
- 本地保存状态
- 阅读器节点内部状态
- 文本节点富文本内容与 AI 输入状态

每次节点移动、尺寸变化、文本输入、生成子节点、标注变化等操作，都会触发 `nodes` 或 `edges` 更新，并进一步触发历史记录、保存状态、渲染节点派生、连线派生和本地快照保存等链路。

## 3. 已确认的卡顿原因

### 3.1 高频操作触发历史记录全量序列化与深拷贝

证据：

- `components/zenme/canvas-client.tsx` 中 `nodes/edges` 变化后调用 `pushCanvasHistory(nodes, edges)`。
- `components/zenme/canvas/geometry.ts` 中：
  - `getCanvasHistorySignature(...)` 使用 `JSON.stringify(...)` 序列化节点和连线。
  - `cloneCanvasState(...)` 使用 `JSON.parse(JSON.stringify(...))` 深拷贝整张画布。

影响：

- 拖动节点时 React Flow 会连续触发 position changes。
- resize 时会连续触发 dimensions changes。
- 文本节点输入时每个字符都会更新节点数据。
- 当节点中包含阅读器、长文本、笔记、图片 URL、标注数据时，单次序列化成本会明显升高。

结论：

这是“每次操作都会卡”的首要原因。

当前已做缓解：

- 拖动和 resize 中的连续变化跳过即时历史记录。
- 普通历史记录改为 500ms 防抖，减少连续输入和微操作时的同步深拷贝。
- 文本节点正文输入改为局部编辑 + 500ms 防抖写回画布节点数据，避免每个字符触发画布级状态更新；blur、格式化操作、AI 提交前仍会立即 flush。

### 3.2 本地快照保存仍需关注大画布写入成本

证据：

- `components/zenme/canvas-client.tsx` 中 `persistLocalSnapshot()` 会对完整 `nodes/edges/viewport` 组成快照。
- 常规本地快照保存已改为 IndexedDB 优先；旧 localStorage 快照仍可兼容读取。
- 刷新/离开页面兜底保存仍会同步写入 localStorage，保证最后编辑尽量不丢失。

影响：

- 相比历史记录，保存已有防抖和 idle 调度，频率较低。
- IndexedDB 避免了常规保存路径的大字符串同步写入，但结构化克隆和快照构建仍有成本。
- 如果用户持续输入、拖动或阅读器内部状态频繁写入节点数据，仍可能造成保存排队和短暂停顿。

结论：

这是第二优先级风险。当前常规保存链路已降级为异步存储，但随着画布数据量增大仍需要继续观测 IndexedDB 写入、结构化克隆和刷新兜底 localStorage 的成本。

当前已做缓解：

- 本地快照保存防抖从 600ms 调整为 1200ms。
- 拖动和 resize 过程中跳过本地快照调度，等待交互结束后再保存。
- 画布保存请求增加并发合并：同一时间只执行一个 `saveCanvas`，保存期间到来的自动保存、手动保存或缩略图保存请求会合并成一次后续保存。
- 本地异步快照保存增加并发合并：同一时间只执行一个 IndexedDB 写入；保存过程中到来的普通本地快照请求合并成一次后续保存。刷新/离开页面兜底仍保持立即写 localStorage。
- 保存前对节点做持久化瘦身，去掉 `selected`、`dragging`、`resizing`、`measured` 和运行时函数字段。
- 常规本地快照保存改为 IndexedDB 优先，localStorage 只作为兼容读取、IndexedDB 失败兜底和刷新前兜底。

### 3.3 缩略图生成依赖 DOM 截图，成本较高

证据：

- `components/zenme/canvas/persistence.ts` 中 `createCanvasThumbnail(...)` 使用 `html-to-image` 的 `toBlob(...)`。
- `saveCanvas(...)` 保存时会调用 `createThumbnail()`，进而截图画布 DOM。

影响：

- `html-to-image` 需要遍历 DOM、计算样式并生成图片。
- 如果画布中包含阅读器、PDF/EPUB 页面、图片和较多节点，截图成本会显著增加。
- 当前主要在后台缩略图刷新和自动保存链路中触发，不一定是“每次操作”的直接原因，但会造成周期性明显卡顿。

结论：

这是第三优先级风险。需要从“每次保存生成缩略图”调整为低频或按需生成。

### 3.4 文本节点富文本编辑高频写入节点数据

证据：

- `components/zenme/nodes.tsx` 中文本节点 `onInput` 调用 `syncEditorContent()`。
- `syncEditorContent()` 会调用 `nodeData.onUpdateTextNode(...)` 更新 `plainText` 和 `richTextHtml`。

影响：

- 每个字符输入都会更新 React Flow 节点数据。
- 节点数据变化会触发画布渲染、保存状态、历史记录、防抖快照等链路。

结论：

这是文本节点输入卡顿的核心原因。历史记录防抖后会缓解，但后续仍应改为局部编辑状态 + 防抖提交到画布节点数据。

### 3.5 阅读器节点内容复杂，易放大画布渲染成本

证据：

- 阅读器作为 `reader` 节点嵌入画布。
- `getRenderedCanvasNodes(...)` 会在节点派生时处理 reader size、projectId、回调等。
- 阅读器内部包含目录、正文/PDF 页面、右侧笔记栏、标注 overlay、滚动监听等。

影响：

- 当画布状态变化导致 React Flow 重新计算节点时，复杂 reader 节点更容易放大渲染成本。
- PDF/EPUB 阅读器中如果页面渲染、标注 overlay 或滚动状态没有隔离，可能被画布级更新牵连。

结论：

这是中长期重点。需要把阅读器内部状态和画布节点状态隔离，避免每个画布操作都触发阅读器复杂子树重渲染。

### 3.6 派生节点和派生连线每次都遍历全量节点

证据：

- `getRenderedCanvasNodes(...)` 每次 `nodes` 变化都会遍历所有节点，并构建 `nodeById`。
- `getRenderedCanvasEdges(...)` 每次 `nodes/edges` 变化都会按 source 查找节点。

影响：

- 小画布影响不明显。
- 节点和连线数量增长后，遍历和查找成本会累积。

结论：

当前优先级低于历史记录和保存链路，但进入多节点、多阅读器、多笔记场景后需要优化。

## 4. 优化目标

### 4.1 体验目标

- 节点拖动应保持连续、无明显掉帧。
- 文本输入不应出现按键后停顿。
- AI 子节点生成后画布不应因保存或历史记录明显卡顿。
- 阅读器打开后，普通画布操作不应被阅读器内容复杂度明显拖慢。
- 定时保存不应造成可感知的大卡顿。

### 4.2 技术目标

- 高频操作路径中不做全量 `JSON.stringify` 和深拷贝。
- 历史记录只保存用户可感知的操作边界，而不是每一帧中间状态。
- 本地保存可被调度、合并、降频。
- 缩略图生成与保存解耦。
- 阅读器和文本编辑器内部状态尽量局部化，减少画布级状态更新。

### 4.3 建议验收指标

首期建议先采用浏览器 Performance 面板和轻量日志验证：

- 拖动节点 3 秒，主线程无连续长任务；单次长任务尽量低于 50ms。
- 连续输入 500 字，输入无明显阻塞，节点内容能在防抖后保存。
- 100 个普通节点 + 20 条边场景下，拖动节点仍可连续响应。
- 打开 1 个阅读器 + 20 个笔记节点场景下，拖动普通文本节点无明显卡顿。
- 保存动作不阻塞当前输入和拖动。

调试入口：

- 开启 `NEXT_PUBLIC_ZENME_PERF_DEBUG=1` 后，可在项目页 URL 增加 `?zenmePerfSeed=200&zenmePerfSeedReplace=1` 生成 200 个文本节点和连线，用于复现大画布渲染、保存、历史记录和 MiniMap 压力；可追加 `zenmePerfEdgesPerRow=4` 增加每行横向连线密度，用于复现多连线场景。
- 本地开发环境也可显式追加 `zenmePerfSeedDebug=1` 启用该入口；生产环境不会响应该开发参数。
- 可追加 `zenmePerfSample=1` 自动执行一次 `fitView` 和画布保存采样；如需同步观察 DOM 截图成本，可再追加 `zenmePerfSampleThumbnail=1`。例如：`?zenmePerfSeed=200&zenmePerfSeedReplace=1&zenmePerfEdgesPerRow=4&zenmePerfSample=1&zenmePerfSampleThumbnail=1`。
- 开启性能调试后，最近 100 条性能指标会保存在 `window.__ZENME_CANVAS_PERF__`，并可通过 `window.__ZENME_CANVAS_PERF_SUMMARY__()` 按 label 汇总 count、平均耗时和最大耗时，便于浏览器控制台或 Playwright 读取。
- 开启性能调试后，节点拖动和 resize 会额外记录 `interaction drag` / `interaction resize` 指标，包含总时长、回调帧数、平均帧间隔和最大帧间隔，用于判断交互过程中是否出现明显掉帧或长间隔。
- 开启性能调试后，阅读器滚动会额外记录 `reading scroll` 指标，包含滚动持续时长、rAF 帧数、平均帧间隔和最大帧间隔。
- 开启性能调试后，浏览器支持 Long Task API 时会自动记录 `long task` 指标，用于观察超过 50ms 的主线程阻塞。

## 5. 分阶段优化计划

### Phase 0：确认与止血

目标：减少最明显的“每次操作都卡”。

已完成或应立即完成：

- 拖动过程跳过历史记录中间帧，只在拖动结束后记录。
- resize 过程跳过历史记录中间帧，只保留最终尺寸。
- 普通历史记录改为 500ms 防抖。

补充建议：

- 增加开发环境性能日志开关，例如 `NEXT_PUBLIC_ZENME_PERF_DEBUG=1`。
- 记录以下耗时：
  - history entry
  - local snapshot build
  - indexeddb snapshot get/put
  - thumbnail generation
  - save total time

验收：

- 文本连续输入和普通节点操作不再每一下触发历史深拷贝。

当前落地状态：

- 已完成首版：新增 `NEXT_PUBLIC_ZENME_PERF_DEBUG=1` 开关，打开后可在控制台看到 `[zenme:perf]` 日志。
- 已完成首版：已记录 history entry、local snapshot build、IndexedDB snapshot get/put、thumbnail toBlob 等关键链路耗时。
- 已完成首版：性能日志会同步写入 `window.__ZENME_CANVAS_PERF__` 环形缓冲，最多保留最近 100 条；新增 `window.__ZENME_CANVAS_PERF_SUMMARY__()` 可按 label 汇总 count、平均耗时和最大耗时，便于自动化测试比较。
- 已完成首版：新增 `zenmePerfSample=1` 自动采样入口，可在性能种子生成后自动记录 `fitView`、保存和可选缩略图生成耗时，降低大画布验证的手动操作成本。
- 已完成首版：新增拖动/resize 交互采样，在 debug 模式下记录 `interaction drag` / `interaction resize` 的持续时间、回调帧数、平均帧间隔和最大帧间隔。
- 已完成首版：新增 Long Task 观测，在 debug 模式下自动记录 `long task` 指标，帮助定位保存、渲染或截图之外的主线程阻塞。
- 已验证：在 debug build 中通过页面内 180ms 主线程任务可记录 `long task` 指标，并写入 `window.__ZENME_CANVAS_PERF__`。
- 已验证：默认不开启时不输出性能日志，不影响正常使用。

### Phase 1：历史记录结构优化

目标：从“全量快照历史”升级为“操作级历史”。

建议实现：

- 拖动节点：只记录拖动前和拖动后的节点位置变化。
- resize 节点：只记录 resize 前和后的尺寸变化。
- 文本编辑：记录编辑前后内容，而不是每个字符。
- 新建/删除/连线/分组：记录明确 command。

可选方案：

- 使用 command stack：
  - `moveNodes`
  - `resizeNode`
  - `updateText`
  - `createNode`
  - `deleteNodes`
  - `connectNodes`
  - `groupNodes`
- 每个 command 提供 `apply` 和 `revert`。

验收：

- undo 行为仍可用。
- 历史记录内存随操作数增长，不随画布总数据体积线性爆炸。
- 大画布拖动时不再需要深拷贝完整 `nodes/edges`。

当前落地状态：

- 已完成过渡版：历史记录仍保持快照式 undo，但历史快照会先剔除 `selected`、`dragging`、`resizing`、`measured` 和运行时函数字段，再生成 signature 和 clone。
- 已完成过渡版：历史 signature 从只关注 `id/type/position/data` 调整为基于瘦身后的完整节点/连线快照，避免 resize、分组关系、尺寸等变化漏记。
- 已完成首版：历史 entry 和 signature 合并为一次瘦身快照生成，避免同一次历史记录重复 stringify/parse。
- 已完成首版：历史 entry 已接入 `NEXT_PUBLIC_ZENME_PERF_DEBUG=1` 性能日志，并记录节点/连线数量。
- 已完成首版：节点拖动和节点 resize 结束后改为 `updateNodes` command 历史，只记录变化节点的 before/after，避免这两类高频操作在结束时深拷贝整张画布。
- 已完成首版：文本节点正文和标题更新接入 `updateNodes` command 历史，只记录单个文本节点更新前后的状态，避免防抖提交后再生成全量画布历史快照。
- 已完成首版：新增 `createCanvasItems` / `deleteCanvasItems` command，用于记录新增节点/连线和删除节点/连线，避免文本节点、笔记节点、阅读器节点、拖入文件、手动连线、删除节点等常见操作生成全量历史快照。
- 已完成首版：新增 `mutateCanvasItems` 复合 command，用于一次记录“新增、删除、更新节点/连线”的组合操作；分组、阅读器折叠/展开、首次图书资料准备并打开阅读器已接入该路径，避免拆成多条历史或落回全量快照。
- 已完成首版：全量历史兜底路径增加 `history fallback snapshot` 指标；如果 debug 采样中出现该指标，说明仍有未 command 化的状态变化需要继续拆分。
- 已完成首版：snapshot 与 command 混合历史通过 replay 计算撤销目标状态，保留原有 Ctrl+Z 使用方式。
- 已验证：文本节点编辑后按 Ctrl+Z，可从“修改后的内容”恢复到“原始内容”，节点和快照仍正常保留。
- 已验证：合并 history entry 后，文本节点编辑再撤销仍可恢复到“原始内容”，本地快照不含运行时字段。
- 后续仍需继续：批量布局和后续新增的复合编辑操作仍可继续按 command 拆分。

### Phase 2：保存链路优化

目标：保存不阻塞交互。

建议实现：

- 将本地保存防抖从 600ms 提高到 1000-1500ms，或根据操作类型动态调整。
- 拖动/resize 期间不执行本地快照写入，停止后再保存。
- 对快照做轻量化：
  - 不保存运行时回调字段。
  - 不保存临时 UI 状态。
  - 阅读器内部可缓存内容不放入节点数据。
- 本地快照写入前先构建可序列化的 `persistedNodes`，减少数据体积。

进一步方案：

- 使用 IndexedDB 替代 localStorage，避免大字符串同步写入主线程。
- 保存任务放入 `requestIdleCallback` 或 worker。

验收：

- 保存时不影响输入和拖动。
- 大画布快照体积可观测并控制在合理范围。

当前落地状态：

- 已完成首版：本地快照防抖调整为 1200ms，拖动/resize 期间不触发快照写入。
- 已完成首版：本地快照在防抖后通过 `requestIdleCallback` 调度写入；不支持该 API 时回退到 `setTimeout(0)`。
- 已完成首版：`saveCanvas()` 增加 in-flight 合并队列，避免自动保存、手动保存、性能采样保存和缩略图周期保存并发触发多次快照构建/本地写入；缩略图请求会保留到最新一轮保存；debug 模式下可通过 `save queue request` / `save queue flush` 观察合并是否发生。
- 已完成首版：`persistLocalSnapshot()` 普通异步保存增加 in-flight 合并队列，避免短时间内多个 idle 保存重复触发快照构建和 IndexedDB 写入；debug 模式下可通过 `local snapshot queue request` / `local snapshot queue flush` 观察合并是否发生。
- 已完成首版：保存前生成 persistable nodes，剔除运行时字段和回调字段。
- 已完成首版：保存状态、本地快照调度和空闲缩略图刷新改为先比较“可持久化画布签名”；节点选中、焦点、测量态等运行时变化不再把画布标记为未保存，也不会触发 IndexedDB 快照写入。
- 已完成首版：开启性能调试时记录 `save snapshot build`、`save snapshot size`、`local snapshot save` 和 `thumbnail write` 等指标，可观察快照体积和本地写入耗时。
- 已完成首版：本地画布快照保存改为 IndexedDB 优先，避免常规保存路径使用 `localStorage.setItem(...)` 同步写入大字符串；旧 localStorage 快照仍可兼容读取。
- 已完成首版：刷新/离开页面的兜底保存保留一次同步 localStorage 写入，优先保证最后编辑不丢失。
- 已完成首版：刷新/离开页面兜底同步写入只在 `未保存` 或 `保存失败` 状态触发；已保存画布刷新不再重复构建并写入大快照。
- 已验证：创建并选中文本节点后，本地快照保留正文内容，但不包含 `selected`、`dragging`、`measured`，且 `data` 中没有函数字段。
- 已验证：idle 调度保存后，本地快照仍能保存最新文本内容，并继续剔除运行时字段。

### Phase 3：缩略图生成降频

目标：缩略图不参与常规高频保存。

建议实现：

- 自动保存只保存 canvas snapshot，不生成缩略图。
- 缩略图只在以下时机生成：
  - 离开项目页。
  - 回到首页/项目列表前。
  - 用户显式保存。
  - 后台 idle 时间。
- 缩略图生成失败不影响保存状态。

可选优化：

- 只截取当前 viewport，不截整张复杂画布。
- 缩略图节点渲染使用轻量快照层，而不是完整 DOM。

验收：

- 保存过程不再因 `html-to-image` 产生明显长任务。
- Dashboard 缩略图仍能按合理频率更新。

当前落地状态：

- 已完成首版：`saveCanvas()` 默认只保存 canvas snapshot，不再默认生成缩略图。
- 已完成首版：用户点击“手动保存”和 6 小时周期保存会生成缩略图。
- 已完成首版：画布变化后的空闲缩略图刷新从 20 秒调整为 6 小时，避免普通编辑过程中频繁触发 DOM 截图。
- 已完成首版：带缩略图保存已拆成“先保存画布快照，再在浏览器空闲期后台生成并保存缩略图”，避免 `html-to-image` 阻塞快照保存主路径。
- 已验证：文本节点普通编辑后，本地项目没有新增缩略图；点击“手动保存”后才生成 `data:image/png` 缩略图。

### Phase 4：文本节点编辑隔离

目标：文本输入不触发画布级状态高频更新。

建议实现：

- 文本节点内部维护 draft state 或直接使用 contentEditable DOM 作为编辑态。
- `onInput` 只更新本地 DOM 或局部 state。
- 防抖后再提交到 `nodes`。
- blur、格式化操作或提交生成子节点前强制 flush。

注意：

- 需要保证刷新前兜底保存。
- AI 生成上下文读取时应优先读 editor DOM 最新内容。

验收：

- 连续输入长文本时 React Flow 节点数据不会每个字符变化。
- 保存仍能拿到最终文本内容。

当前落地状态：

- 已完成首版：文本节点 `onInput` 不再每个字符直接写回 `nodes`，改为 500ms 防抖。
- 已验证：连续输入 419 字后，快照保存的 `plainText` 长度与输入一致；AI 请求上下文包含最新正文。

### Phase 5：阅读器渲染隔离

目标：阅读器复杂内容不拖慢画布整体操作。

建议实现：

- 阅读器内部状态放在阅读器组件或独立 store，避免写回画布节点数据。
- PDF/EPUB 页面继续虚拟化，只渲染视口附近页面。
- 阅读器节点拖动/缩放时，暂停或降级内部重计算。
- 标注 overlay 和选区状态不进入画布级 nodes。

验收：

- 打开阅读器后拖动其他节点不出现明显卡顿。
- 阅读器滚动不触发画布保存/历史记录。

当前落地状态：

- 已完成首版：阅读器滚动处理改为 `requestAnimationFrame` 合并，滚动事件只调度下一帧计算，降低连续滚动时的 DOM 测量和状态更新频率。
- 已完成首版：阅读器滚动接入 debug-only `reading scroll` 指标，记录滚动持续时长、rAF 帧数、平均帧间隔和最大帧间隔，便于定位 PDF/EPUB/TXT 阅读中的滚动卡顿。
- 已完成首版：阅读进度保存改为 600ms 防抖合并，快速滚动跨多个章节时只保存最后停留章节；组件卸载时会兜底保存待提交进度。
- 已完成首版：`PdfReadingView`、`EpubPagedScrollView`、`ReadingTextSectionsView` 使用 `memo(...)` 包装，减少阅读器父组件中无关状态变化对重内容视图的牵连。
- 已完成首版：阅读器 header、目录侧栏、笔记侧栏和单个笔记卡片使用 `memo(...)` 包装，并稳定笔记 CRUD、排序、跳转和目录操作回调，减少滚动进度、目录选择、笔记编辑之间的无关重渲染。
- 已完成首版：笔记拖拽排序状态、拖放指示器、笔记编辑草稿状态已下沉到 `ReadingNotesSidebar`，编辑/拖动笔记卡片时不再更新 `ReadingWorkspace` 父组件状态，减少正文视图被笔记栏轻状态牵连重渲染。
- 已完成首版：TXT/EPUB 正文页拆为 memo 化的单页组件，并将文本选区预览拆为独立 overlay；选区变化时只更新相关页的预览层，减少整本文本/EPUB 可见页重新生成高亮 HTML。
- 已完成首版：TXT/EPUB 单页正文的高亮 HTML 使用 `useMemo(...)` 缓存；选区预览浮层变化不会再触发正文高亮 HTML 重新生成。
- 已验证：预置文本节点、阅读器节点和连线后页面正常渲染，无运行时错误。
- 后续仍需继续：阅读器 payload、PDF 标注选择等内部状态还在同一个组件中，后续可进一步拆分为局部 store 或更细组件，减少目录/正文/标注层之间的互相重渲染。

### Phase 6：派生数据和渲染优化

目标：节点数增长后仍可扩展。

建议实现：

- `getRenderedCanvasEdges(...)` 使用 `nodeById` Map，避免 edges.map 中重复 nodes.find。
- `getRenderedCanvasNodes(...)` 只对 reader/text/group 做必要派生。
- 对节点组件使用 `memo`，避免无关节点重渲染。
- 大量节点场景下关闭或简化 MiniMap 节点渲染。

验收：

- 100-300 节点画布下，选择、拖动、连线仍保持可操作。

当前落地状态：

- 已完成首版：`getRenderedCanvasEdges(...)` 从每条边 `nodes.find(...)` 改为 `Map` 查找，避免节点和连线数量增长后形成 `nodes × edges` 的重复扫描。
- 已完成首版：连线派生依赖从完整 `nodes` 数据收窄为 `nodeId:kind` 签名，文本内容、位置和尺寸变化不会单独触发连线派生重算。
- 已完成首版：画布节点组件通过 `memo(...)` 包装，降低无关节点被父级渲染牵连的概率。
- 已完成首版：`createTextChildNode` 不再依赖完整 `nodes/edges`，减少文本节点注入回调的引用变化。
- 已完成首版：`getRenderedCanvasNodes(...)` 对文本节点和阅读器节点增加 WeakMap 派生结果缓存；当原始 node 引用和注入回调未变化时，复用上一轮渲染 node，提升 `memo(...)` 的实际收益。
- 已完成首版：React Flow 开启 `onlyRenderVisibleElements`，大画布下只渲染视口附近元素，减少不可见节点/连线的 DOM 与 React 渲染压力。
- 已完成首版：节点拖动和 resize 期间临时暂停 MiniMap 的真实渲染，保留同尺寸白色占位，避免小地图在高频节点变化时跟随重算。
- 已完成首版：新增大画布性能种子入口，可按 URL 参数生成 1-500 个文本节点和连线，并可用 `zenmePerfEdgesPerRow` 调整每行连线密度，用于稳定复现 100-300 节点、多连线场景并配合性能日志观察。
- 已完成首版：新增大画布自动采样入口 `zenmePerfSample=1`，可在种子画布加载后自动执行 `fitView` 和保存采样，配合 `zenmePerfSampleThumbnail=1` 观察缩略图 DOM 截图成本。
- 后续仍需继续：阅读器内部组件状态和画布节点状态仍需进一步隔离，避免阅读器复杂子树被画布级变化牵连。

## 7. 当前已落地的优化

截至本报告创建时，代码中已完成：

### 7.1 性能观测能力

性能观测体系是本轮优化中最重要的基础设施之一。它的目标不是只解决某一次卡顿，而是让后续所有“画布变慢”“阅读器变卡”“保存阻塞”“缩略图截图耗时”等问题都能先被量化，再决定优化方向。

已建立的观测入口：

- `NEXT_PUBLIC_ZENME_PERF_DEBUG=1`：统一性能日志开关。开启后会输出 `[zenme:perf]` 日志，并把指标写入浏览器窗口对象。
- `window.__ZENME_CANVAS_PERF__`：最近 100 条性能指标环形缓冲，便于在控制台或 Playwright 中读取原始样本。
- `window.__ZENME_CANVAS_PERF_SUMMARY__()`：按 label 汇总最近样本的 count、平均耗时、最大耗时、总耗时和最近一次 detail，适合快速判断当前最慢链路。
- `long task` 指标：浏览器支持 Long Task API 时，会记录超过 50ms 的主线程阻塞，用于把用户感知卡顿和具体时间窗口关联起来。
- `interaction drag` / `interaction resize`：记录节点拖动、调整尺寸过程中的持续时间、回调帧数、平均帧间隔和最大帧间隔。
- `reading scroll`：记录 PDF/EPUB/TXT 阅读器滚动过程中的持续时间、rAF 帧数、平均帧间隔和最大帧间隔。
- `history fallback snapshot`：当操作仍落回全量历史快照时记录指标，用于发现还没有 command 化的复合编辑操作。
- 保存链路指标：覆盖 `save snapshot build`、`save snapshot size`、`local snapshot save`、`indexeddb snapshot put/get`、`thumbnail toBlob` 和 `thumbnail write` 等关键路径。
- `zenmePerfSeed`：可通过 URL 参数生成 1-500 个文本节点和连线，用于稳定复现大画布压力场景。
- `zenmePerfEdgesPerRow`：控制每行横向连线密度，用于复现多连线场景。
- `zenmePerfSample=1`：自动执行一次 `fitView` 和保存采样。
- `zenmePerfSampleThumbnail=1`：在自动采样中追加缩略图 DOM 截图耗时。

建议排查流程：

1. 先开启 `NEXT_PUBLIC_ZENME_PERF_DEBUG=1`，复现卡顿操作。
2. 在控制台查看 `window.__ZENME_CANVAS_PERF_SUMMARY__()`，先确认最高耗时来自保存、历史、渲染、缩略图、阅读器滚动还是 Long Task。
3. 如果需要稳定复现大画布问题，使用 `zenmePerfSeed`、`zenmePerfEdgesPerRow` 和 `zenmePerfSample=1` 生成固定压力场景。
4. 如果 summary 里出现 `history fallback snapshot`，优先继续把对应操作 command 化。
5. 如果 Long Task 与 `thumbnail toBlob` 或缩略图写入重叠，优先检查缩略图保存路径。
6. 如果 Long Task 与 `reading scroll` 重叠，优先拆分阅读器内部状态或继续缩小正文/标注层重渲染范围。

这套观测能力后续应作为性能优化的前置步骤：新增复杂节点、阅读器能力、视频节点、批量布局或 AI 生成子节点前，都应先确认关键交互是否能被采样和归因。

## 8. 风险与注意事项

- 历史记录防抖会改变 undo 粒度，需要确认用户预期：连续输入应作为一次编辑还是多次编辑。
- 跳过拖动中间帧后，undo 应回到拖动前位置，而不是中间位置。
- 刷新/离开页面兜底仍会在存在未保存变更时同步写入 localStorage，大画布下可能有短暂停顿；已保存状态会跳过该兜底写入，常规保存路径已改为 IndexedDB 优先，后续可继续评估 worker 化或更精细的增量保存。
- 缩略图降频会让首页缩略图更新不那么实时，需要产品侧接受“稍后更新”的表现。
- 阅读器节点作为画布节点是产品关键设计，不应为了性能退回模态窗；优化方向应是隔离和虚拟化。

## 9. 下一步建议

下一步建议进入真实大画布验证和 Phase 2/5 的深水区优化：

- 用 `zenmePerfSeed` 生成 100-300 节点、多连线场景，并配合 `zenmePerfSample=1` / `window.__ZENME_CANVAS_PERF__` 记录首轮 `fitView`、保存、缩略图生成耗时；拖动/resize 可先看 `interaction drag` / `interaction resize`，阅读器滚动可先看 `reading scroll` 和 `long task`，再用 Performance 面板补充真实 PDF/EPUB 文件的帧率采样。
- 验证 IndexedDB 保存路径在真实大画布下的耗时收益，并继续评估 worker 化或增量保存，减少快照构建和结构化克隆成本。
- 继续拆分阅读器内部状态，优先隔离笔记栏、目录、标注选择状态，避免普通画布操作牵连 PDF/EPUB 重内容视图。
- 将批量布局和后续新增的复合编辑操作继续 command 化，使历史记录逐步完全摆脱全量快照。
